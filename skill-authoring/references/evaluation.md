# 触发与实际任务评估

仅在设计用例、行为评估或修订失败技能时读取。预期结果来自真实需求与契约，不能由生成产物反向决定。

## 分四层记录

1. 结构：metadata、文件与引用是否在检查范围通过；未支持的写法单列。
2. 选择：只给名称、description 和请求，评估者是否选择正确；不把已显式要求使用技能的任务记作隐式触发测试。
3. 执行：给真实任务、技能及必要原始输入，在隔离目录生成实际产物；核对结果与副作用。
4. 宿主：记录工具版本、OS、启动目录与真实发现/调用情况；格式相同不代表宿主能力相同。

本工厂的 [cases.json](../evals/cases.json) 是可复用用例资料，不会调用模型或产生自动触发率。选择评估时仅给出 prompt 与候选 metadata，保留 expected 用于事后评分；执行时不要把评分答案塞进任务。

## 选择低成本且有信号的用例

新技能的起点可为 3 个正例、3 个反例、2 个边界/前提缺失例，按误触发/漏触发成本调整。用新的措辞检验是否只记住例子，解释边界而不堆关键词。

实质产物验证以两个彼此独立的代表任务为起点，至少一个未用于写技能。用户未提供或未授权真实素材/执行时，完成可做的验证并列出回放缺口，不扩展任务。昂贵的图片/模型生成可缩小样本，配合低成本结构检查；说明只验证了哪些场景。对格式工具脚本使用正常和错误输入，测试退出码与实际文件，避免仅比较实现细节。

## 最小记录

每条记录保存任务 ID、输入/工具前提、技能版本或指纹、实际动作/产物路径、观察、失败与未验证项。[rubric.md](../evals/rubric.md) 是可选参考；被限制访问或不适用时，先从原始任务建立验收契约，明确使用的标准，不猜测默认评分答案。仅在授权写入时把记录保留在指定隔离目录；只读评估可在回复中报告。

观察应包括：选得对、范围没扩大、必要信息齐、资源确实可读/可执行、产物达标、缺前提能正确停止。没有真实 CAD、图像或建模工具时，不能由文字宣称对应工程产物已验证。

## 失败驱动修订

先区分触发误判、信息不足、资源/工具失败和流程错误，再调整对应部分。修订后重放失败例、相邻正常例，再看新的输入。保留反例，避免把单次失败变成所有任务都必须经过的审批或长检查表。

本地用例和独立评估也有样本限制；记录有限范围的结果，不写“所有工具兼容”“永不越权”或“质量百分百”。
