# Bug 复现与根因定位

交付能区分原因的证据、受影响范围和最小修复方向。调查与修复分别按当前授权执行；用户已经要求修复时，完成调查后可以继续修复，不重复索要授权。只要求分析时保持业务文件只读。

## 输入与项目约束

确认异常入口、实际现象、预期行为、版本/环境和相关改动。截图或日志是线索，不能单独证明根因。缺少复现步骤时先从代码、测试及现有材料补足；只有会改变调查方向的信息才询问用户。

先读当前项目适用的 AGENTS、模块契约和验证入口，记录分支及已有暂存/未暂存/未跟踪内容。区分本轮要求与附件参考，不覆盖用户改动。处理 inspect-frontend 仓库时读 [本项目调查导航](references/project-context.md)；其他项目重新定位自身入口，不套用该案例的框架或业务政策。

## 从现象到原因

1. 固定一个最小可复现情形：操作顺序、输入、初始状态、触发时机、实际/预期结果。间歇问题记录重复次数和时序；使用隔离样本时明确其来源。无法运行时把静态调查和运行缺口分开。
2. 沿真实入口追到数据和状态拥有者，检查调用者、共享消费者及清理路径。不要把异常最终显示的位置直接当作出错位置，也不要把截图里的推测当成接口契约。
3. 列出少量可证伪的假设，为每个假设选择一个能区分它的观测或对照。优先排查最贴合现象和近期变更的原因；保留否定证据，避免同时改多处后失去因果关系。
4. 对异步问题比较创建、完成、取消和提交状态的先后顺序。分别检查设备/路由切换、晚到响应、取消后回调和卸载；Promise 拒绝、取消请求和阻止旧状态提交不是同一件事。
5. 对 UI/三维问题分别观察模型/业务状态、屏幕投影、排布目标、动画中间值和 DOM 实际尺寸。用真实浏览器验证可视行为；纯逻辑回放不能证明遮挡、文字换行或用户操作已通过。
6. 用最小反例或对照确认机制。尽量证明同一输入下修复前失败、修复后满足预期；若本轮只调查，可在授权的隔离目录验证候选机制，不改业务源。根因尚未确认时明确剩余假设与下一个区分实验，不强行给出确定答案。

临时观测避免记录密钥、完整请求头和个人数据。使用已有工具；缺后端、权限或运行环境时，缩小到仍能执行的验证，不安装依赖或编造联调结果。

## 修复与回归

已有修复授权时，仅修改确认的原因及必要调用方，保留现有复用、空态和生命周期契约。验证原反例、相邻正常情形及受影响消费者；测试选择来自项目的验证政策，不能用一个子项目的检查替代另一个。格式、Lint、类型检查和真实行为测试各自说明覆盖边界。

一次实验无法区分假设时先调整观测。连续实验没有新增证据时，交付已知事实、阻塞条件和最有价值的下一步；不通过扩大重构或无限重试制造完成感。

## 交付与验证

报告应包括：复现步骤；预期/实际结果；根因及对应文件位置、时序或观测；已排除的主要假设；影响范围与最小修复建议。实施过修复时列实际改动、执行命令/目录/退出码和回归结果。区分已证实、推断、未运行、环境阻塞及待现场核实项。

评估本技能时使用 [任务用例](evals/cases.json)。这些是人工或 Agent 执行的任务及验收标准，不会自动运行模型；不能把 JSON 存在、关键词命中或结构检查当作根因定位通过。触发评估与实际任务结果分别记录。
