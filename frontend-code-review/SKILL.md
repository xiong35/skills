# 有证据的前端代码审查

交付可行动的问题及验证缺口，不默认修改代码。审查范围与修复范围分开；若用户明确同时要求修复，按授权继续，并区分原发现与修复后的结果。

## 先确定审查对象

明确用户指的是工作区、暂存区、某次提交、分支差异还是指定文件/调用链。记录分支、基线 SHA 和工作树；检查 staged、unstaged 及相关 untracked 文件，避免遗漏新文件或把别人的改动混进范围。没有明确基线时先查上下文；仍有多种实质不同解释时询问，不自行选择远程主干作为答案。

读适用 AGENTS、需求与模块契约。处理 inspect-frontend 时读 [本项目审查导航](references/project-context.md)；在其他项目重新确认栈、自动导入、数据和验证方案，不复制本仓库特例。

变更审查只报告本次引入或加重的问题；已有缺陷单独说明来源。用户明确要求现状审计时可以审查存量问题，不把所有历史问题伪装成本次回归。

## 验证候选问题

沿 diff → 调用者 → 数据来源/副作用 → 共享消费者读取必要代码。针对变更选择检查方向，避免为小改动强制全仓审计：

- 请求/状态：真实响应形状、空值与零值、长 ID、请求范围、并发与晚到响应是否改变当前页面。
- 组件/交互：既有 props/events、权限、键盘和点击行为、空态；复用是否保留行为而非仅复制样式。
- 复用与必要性：检查新增组件、工具、请求封装及兜底的已有对应实现，读取真实消费者，核对输入输出、状态和资源所有权。已有能力满足同一契约时，指出可直接复用的位置；存在有效差异时保留必要适配，不按名称或相似代码强制合并。
- 路由/实时资源：重入、参数更新、导航取消、监听解除和资源所有者；共享连接是否被单页清理误关。
- 渲染/布局/性能：真实尺寸与缩放、长内容、动画取消及帧任务、必要的浏览器观测。性能问题要有规模/频率或测量依据。
- 安全与边界：用户可控输入是否到达危险输出、权限检查是否仍有效、日志或资源是否暴露敏感内容；不能仅因存在一个敏感 API 就断言可利用。

对每个候选写清触发条件、执行路径、可观察后果和证据。先查框架配置、相邻实现和契约，排除自动导入、有效零值、已有上游过滤等反证。偏好、格式建议、没有触发路径的猜测不作为缺陷；无法确认的风险列为待验证问题。

按项目已有能力做最小验证：运行针对性测试、构造隔离反例或浏览器操作；只读审查不向业务源加入测试补丁。测试和构建通过不意味着无缺陷，环境缺失也不意味着缺陷已证实。不默认安装依赖、开启服务对外访问或修改后端。

## 输出可行动发现

按实际影响排序，每项包含严重度、简短标题、准确文件/最小行号范围、触发情形、后果、证据及修复方向。优先级按项目约定；没有约定时 P0 表示普遍阻断/严重破坏，P1 表示核心功能或数据安全严重受损，P2 表示特定情形的功能错误，P3 表示低影响问题。不要因为缺少测试就把推测升级为 P1。

变更审查尽量锚定引入问题的变更行，解释跨文件因果；不要把发现只挂到下游报错行。不得凭记忆填写行号。重复同一根因合并，说明所有受影响路径。无确认缺陷时直接说明本范围未发现已确认问题，并列实际验证、覆盖范围和剩余风险；不凑数量，也不声明项目完全正确。

重复实现、多余封装或文档等仅影响维护成本时，单列维护建议，给出对应旧实现、契约比较、替代方式及受影响消费者。只有证实造成行为错误或违反明确项目要求时，才按其实际影响列入缺陷。建议抽取公共能力时说明迁移范围和收益，不为消除几行重复扩大重构。

审查报告之外，不自动暂存、提交、发布或改写用户代码。评估技能可使用 [任务用例](evals/cases.json)，分别检查选择边界、发现真实性、误报、遗漏和只读行为；这些用例不是自动审查引擎或宿主兼容证明。
